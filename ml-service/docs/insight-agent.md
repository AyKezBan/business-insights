# Агент инсайтов

На вход приходят профиль компании, роль пользователя и событие. На выходе карточка инсайта: что произошло, почему это важно именно этой компании, риски, возможности, что делать и что по теме говорит аналитика банка.

## Как работает

```
профиль + событие
  1. разбор события (лёгкая модель, результат кешируется по event_id)
  2. план (LLM; если не получилось - план по правилам)
  3. инструменты по плану
     фрагментов банка нет -> повторный поиск по каналам влияния с мягким порогом
  4. персонализация под компанию и роль
  5. проверка правилами в коде
     есть ошибки -> исправление по замечаниям, до 3 раз
     не исправилось -> неподтверждённые утверждения убираются, status = limited
  6. инсайт + трасса
```

Разбор события не зависит от компании, поэтому он делается один раз, а персонализация - для каждой пары "компания + роль". Факты у всех получаются одинаковые, а вызовов LLM меньше.

Цикл написан без LangGraph. Все шаги работают с общим состоянием (`agent/state.py`).

## Связь события с компанией

У события есть каналы влияния, у компании - признаки из профиля. Соответствие задано в `tools/profile.py`:

| Признак | Каналы |
|---|---|
| кредиты, лизинг | стоимость долга, ликвидность |
| депозиты | доходность размещения |
| факторинг | ликвидность, контрагенты |
| зарплатный проект | затраты на персонал |
| ВЭД и страны | курс, импорт, экспорт, санкции |
| ОКВЭД | каналы отрасли |
| крупные контрагенты по платежам | риск контрагента |
| ОКВЭД компаний группы | каналы отраслей группы |

Неизвестное поле профиля остаётся `null` и попадает в `missing_data`. Выручка ровно 1000 считается заглушкой (пропуск в данных). Денежные поля профиля (`revenue_rub`, `group_revenue_rub`, `amount_rub`) - `Decimal`: в JSON принимаются числом или строкой, например `"2400000000"`.

Роли: `owner`, `ceo`, `cfo`, `chief_accountant`, `treasurer`. Факты и позиция банка у всех ролей одни и те же, меняются акценты и действия.

## Карточка

Схема - `contracts/ml/insight.schema.json`.

- `what_happened` - факты со ссылкой на источник
- `why_it_matters` - выводы со ссылкой на признаки профиля
- `consequences`, `risks`, `opportunities` - у рисков и возможностей есть `level` и `horizon`
- `actions` - что сделать
- `bank_view` - позиция аналитики банка, `model_vs_bank` - где модель с ней не согласна
- `sources`, `profile_features_used`, `missing_data`, `self_check` - на чём основан вывод
- `impact_level`, `scenarios`, `status`, `disclaimer`

У каждого утверждения есть тип: `fact`, `assessment` (позиция банка), `inference` (вывод модели), `hypothesis`, `recommendation`, `unavailable`.

Шкала влияния:
- low - влияние косвенное, действий не требуется
- medium - заметно влияет на один показатель или процесс
- high - сильно влияет на результат, долг или ликвидность

## Статус и outcome

`status` отражает исполнение, `outcome` - содержание. Значение `status=complete` соответствует `succeeded` в спецификации D06 (переименование в контракте отложено до согласования с Backend).

| status | outcome | error_code | Когда |
|---|---|---|---|
| complete | full | - | полный ответ, все проверки пройдены |
| limited | limited | - | часть вывода убрана или нет аналитики банка, но есть обоснованное содержание |
| limited | refused | - | после проверки не осталось ни одного обоснованного вывода по «почему важно» и «последствиям» |
| failed | none | `llm_error`, `budget_run`, `budget_daily` | технический сбой или исчерпан лимит |

У каждого утверждения есть `claim_id` вида `<insight_id>:c<N>` (порядок разделов фиксирован: факты, почему важно, последствия, риски, возможности, действия, позиция банка). `request_id` и `parent_run_id` из запроса возвращаются в карточке без изменений, `version` пока всегда 1.

## Проверка ответа модели

`agent/critic.py`:
- факт и позиция банка должны ссылаться на источник из найденных
- позиция банка ссылается только на фрагменты аналитики банка
- числа в фактах должны быть в источниках или профиле
- признаки компании должны быть в профиле
- все разделы карточки заполнены
- вывод опирается минимум на два признака компании, а не пересказывает новость

## Инструменты

- `search_bank_analytics` - поиск по фрагментам аналитики банка
- `search_news` - связанные новости
- `get_company_signals` - признаки профиля и их каналы

Вызвать можно только их, аргументы проверяются по схеме, число вызовов ограничено. Поиск - BM25 по JSONL.

## Модели и лимиты

Разрешённые модели перечислены в `llm.py`, другие не вызываются. Лёгкая модель - разбор и план, основная - персонализация, запасная - если провайдер вернул ошибку. Лимиты на запуск: 3 итерации проверки, 12 вызовов инструментов, 40 000 токенов. Есть общий дневной лимит токенов.

### Бюджет в рублях

Лимит кейса - 500 руб. в сутки на общий ключ. Сервис считает свои вызовы в `Decimal` (`budget.py`): цена модели за 1000 токенов на вход и на выход, перед вызовом резервируется верхняя оценка, после ответа списывается фактическая стоимость. Вызов, который вышел бы за 500 руб., не отправляется (`budget_daily`).

| Потрачено за сутки | Что делает агент |
|---|---|
| меньше 350 руб. | работает как обычно |
| от 350 руб. | в начале запуска пишет в трассу `budget.level = warn` |
| от 450 руб. | пропускает необязательные шаги: повторный поиск по банку и исправление по замечаниям; карточка получает `limited` и пометку в `missing_data` |

Остальное:
- счётчик лежит в `TRACE_DIR/budget_state.json` (или `BUDGET_STATE_PATH`), переживает рестарт, сутки считаются по `BUDGET_TIMEZONE` (по умолчанию Europe/Moscow, границу суток провайдера надо подтвердить);
- цены задаются `LLM_PRICES_JSON`, для неизвестной модели берутся завышенные цены по умолчанию. **Тарифы провайдера пока не подтверждены**, без реальных цен рублёвый учёт приблизительный;
- сервис не видит расход других участников на тот же ключ: нужен запас в лимите или общий учёт на стороне Backend;
- на один запуск есть предел по времени `AGENT_MAX_SECONDS` (120 с): проверяется перед каждым вызовом LLM, при превышении `failed` с `error_code=timeout`;
- у каждого вызова LLM в трассе есть `call_id` и `cost_rub`, в финальном событии `usage` (токены, вызовы, рубли, длительность), `GET /health` показывает `daily_spent_rub`.

## Повторы и версии

- Запрос с `request_id`: повтор с тем же содержимым возвращает готовый инсайт (`cache_hit=true`, тот же `run_id`) без вызовов LLM; тот же `request_id` с другим содержимым - `409`. Одновременные одинаковые запросы выполняются один раз. Неудачный запуск (`failed`) не запоминается: повтор считается новым запуском, его стоит отправлять с `parent_run_id`. Соответствие `request_id` хранится в памяти процесса (не больше 500 последних), после перезапуска повтор выполнится заново.
- Готовые инсайты сохраняются в `TRACE_DIR/insights/`, поэтому `POST /v1/insights/{id}/questions` работает и после перезапуска. Папка содержит данные компаний, в гит не коммитится.
- Разбор события кешируется по хешу текста источников, `PROMPT_VERSION` и модели: изменение новости, промптов или правил проверки даёт новый разбор.
- `PROMPT_VERSION` - хеш файлов промптов и проверок (`agent/versions.py`), `GIT_SHA` берётся из переменной окружения при сборке. Оба, `request_id`, `parent_run_id` и модели пишутся в стартовое событие трассы.

## Безопасность

- текст новостей и аналитики передаётся модели как данные, инструкции из него не выполняются
- действия в карточке - только рекомендации, сервис ничего не делает за пользователя
- в трассу не пишутся промпты (только хеш и длина) и ключи

## Трасса

События: `plan`, `tool_call`, `llm_call`, `check`, `adapt`, `error`, `final`. Схема - `contracts/ml/trace-event.schema.json`. Трасса пишется в JSONL и отдаётся через `GET /v1/runs/{run_id}/trace`.

## Тесты

`tests/test_orchestrator.py` проверяет сценарии:
- данных хватает -> `complete`
- нет аналитики банка -> поиск расширяется, `bank_view = unavailable`, `limited`
- модель выдумала число -> исправление по замечаниям -> `complete`; ошибка повторилась -> утверждение убрано, `limited`
- планировщик упал -> план по правилам
- разбор события один на разные роли
- бюджет исчерпан -> LLM не вызывается, `failed`

Всего 43 теста, LLM в них заменена фейковым клиентом.
