# Агент инсайтов

На вход приходят профиль компании, роль пользователя и событие. На выходе карточка инсайта: что произошло, почему это важно именно этой компании, риски, возможности, что делать и что по теме говорит аналитика банка.

## Как работает

```
профиль + событие
  1. разбор события (лёгкая модель, кеш закреплён за содержимым, cutoff и версиями правил)
  2. план (LLM; если не получилось - план по правилам)
  3. инструменты по плану
     фрагментов банка нет -> повторный поиск по каналам влияния с мягким порогом
  4. персонализация под компанию и роль
  5. проверка правилами в коде
     есть ошибки -> исправление по замечаниям, до 3 раз
     не исправилось -> неподтверждённые утверждения убираются, status = limited
  6. один структурированный смысловой разбор итогового черновика
     нет полного verdict или проверка не завершена -> непроверенные утверждения исключаются
  7. инсайт + трасса
```

Разбор события не зависит от компании, поэтому он делается один раз, а персонализация - для каждой пары "компания + роль". Факты у всех получаются одинаковые, а вызовов LLM меньше.

Цикл написан без LangGraph. Все шаги работают с общим состоянием (`agent/state.py`).

## Мультиагентная схема

Один запуск ведут пять агентов с общим состоянием (`agent/state.py`) и общей трассой. Каждое событие трассы содержит поле `agent`, по нему видно, кто что делал.

| Агент | Что делает | LLM | Почему отдельно |
|---|---|---|---|
| `analyst` | разбор события: факты, участники, каналы влияния; не зависит от компании, кешируется | лёгкая | общий для всех компаний, считается один раз |
| `planner` | решает, какие источники нужны; всегда добавляет поиск по открытым источникам | лёгкая | дешёвая модель, при сбое план по правилам |
| `researcher` | вызывает инструменты: банк, связанные новости, открытые официальные источники; повторный поиск при нехватке | нет | детерминированный, числа считает код, поэтому ему нельзя ошибиться, как модели |
| `personalizer` | выводы для компании и роли: последствия, риски, возможности, действия | сильная | связывает источники с данными компании |
| `verifier` | проверяет ссылки/числа/границы цитат кодом; затем проверяет смысл итогового текста одним структурированным batch | та же основная модель и общий бюджет запуска | отдельный шаг проверки; его вывод не является математическим доказательством истины |

Отдельно работает `qa` (уточняющие вопросы по готовой карточке) и `orchestrator` (сборка карточки, статус). Агенты обмениваются структурированными данными (схемы в `schemas.py`), а не свободным текстом. Разделение выбрано, чтобы не отдавать модели то, что надёжнее делает код: поиск, арифметику и проверку чисел.

## Открытые официальные источники

Агент `researcher` умеет искать не только в локальном корпусе, но и в открытых источниках Банка России (`research/`). Что искать, определяет профиль клиента (код, не LLM):

| Признак профиля | Что берётся |
|---|---|
| кредиты, лизинг, депозиты, факторинг или канал стоимости долга и ликвидности | ключевая ставка с датой действия, предыдущим значением и изменением в п.п. |
| ВЭД по данным ФТС или канал курса | официальные курсы валют по странам из ФТС (КИТАЙ -> CNY, ТУРЦИЯ -> TRY и т. д.; без распознанных стран USD, EUR, CNY) и их изменение за 30 дней |
| каналы влияния события, совпавшие с каналами компании, и слова из названия ОКВЭД | пресс-релизы Банка России, подходящие по началу слов в заголовке |

Если в профиле нет ничего, что требует поиска, запросов в сеть нет.

Точность чисел:
- ставка и курсы берутся из официальных таблицы и XML Банка России, числа хранятся как `Decimal`, текст документа формирует код (запятая как разделитель, округление половина вверх), модель его не пересказывает;
- каждый документ имеет ссылку, дату, время получения и хеш текста (`content_sha256`), проверяется до использования;
- числа в выводах проверяет `verifier` по тексту документов; текущее значение ставки отличается от предыдущего: предыдущее нельзя выдать за текущее (`keyrate_value_mismatch`);
- срез по времени: показатели берутся на дату `as_of` (иначе на дату события), пресс-релизы позже этой даты не используются;
- загрузка только по `https` с `cbr.ru`, лимит 2 МБ, без перенаправлений на другие хосты, XML без DTD и сущностей; недоступный источник пишется в трассу (`open_research`) и не мешает остальным;
- кеш ответов с TTL (15 минут для текущих данных, 30 дней для прошлых дат), папка `TRACE_DIR/open_cache`. Отключить поиск: `OPEN_RESEARCH_ENABLED=false`.

Не охвачено: Росстат (инфляция, занятость) и Минэкономразвития не отдают открытый машиночитаемый канал, который удалось проверить; ленты `government.ru` доступны только по `http` и содержат мало экономических материалов. Новые источники добавляются адаптером в `research/` и записью в `ALLOWED_HOSTS`.

## Связь события с компанией

У события есть каналы влияния, у компании - признаки из профиля. Соответствие задано в `tools/profile.py`:

| Признак | Каналы |
|---|---|
| кредиты, лизинг | стоимость долга, ликвидность |
| депозиты | доходность размещения |
| факторинг | ликвидность, контрагенты |
| зарплатный проект | затраты на персонал |
| ВЭД (наличие в данных ФТС) | курс, санкции; направление сделок в ФТС неизвестно, импорт и экспорт из страны не выводятся |
| ОКВЭД | каналы отрасли |
| крупные контрагенты по платежам | риск контрагента; роль «поставщик/покупатель» не утверждается, переводы себе исключены, доля переводов себе указана в примечании к контрагентам; номер `counterparties[i]` совпадает с номером в отправленном списке |
| ОКВЭД компаний группы | каналы отраслей группы; роль каждой компании и перенос вывода на другую компанию группы не установлены |

Неизвестное поле профиля остаётся `null` и попадает в `missing_data`. Выручка ровно 1000 считается заглушкой (пропуск в данных). Денежные поля профиля (`revenue_rub`, `group_revenue_rub`, `amount_rub`) - `Decimal`: в JSON принимаются числом или строкой, например `"2400000000"`.

Роли: `owner`, `ceo`, `cfo`, `chief_accountant`, `treasurer`. Факты и позиция банка у всех ролей одни и те же, меняются акценты и действия.

## Карточка

Схема - `contracts/ml/insight.schema.json`.

- `what_happened` - факты со ссылкой на источник
- `why_it_matters` - выводы со ссылкой на признаки профиля
- `consequences`, `risks`, `opportunities` - у рисков и возможностей есть `level` и `horizon`
- `actions` - что сделать
- `bank_view` - позиция аналитики банка; `model_vs_bank` пока всегда пуст
- `sources`, `profile_features_used`, `missing_data`, `self_check` - на чём основан вывод
- `impact_level`, `scenarios`, `status`, `disclaimer`

У каждого утверждения есть тип: `fact`, `assessment` (позиция банка), `inference` (вывод модели), `hypothesis`, `recommendation`, `unavailable`.

Шкала влияния:
- low - влияние косвенное, действий не требуется
- medium - заметно влияет на один показатель или процесс
- high - сильно влияет на результат, долг или ликвидность

## Статус и outcome

`status` отражает исполнение, `outcome` - содержание. Значение `status=complete` соответствует `succeeded` в спецификации D06 (переименование в контракте отложено до согласования с Backend).

| status | outcome | error_code | Когда |
|---|---|---|---|
| complete | full | - | полный ответ, все проверки пройдены |
| limited | limited | - | часть вывода убрана или нет аналитики банка, но есть обоснованное содержание |
| limited | refused | - | после проверки не осталось ни одного обоснованного вывода по «почему важно» и «последствиям» |
| failed | none | `llm_error`, `budget_run`, `budget_daily` | технический сбой или исчерпан лимит |

У каждого утверждения есть `claim_id` вида `<insight_id>:c<N>` (порядок разделов фиксирован: факты, почему важно, последствия, риски, возможности, действия, позиция банка). `request_id` и `parent_run_id` из запроса возвращаются в карточке без изменений, `version` пока всегда 1.

## Проверка ответа модели

`agent/spans.py` проверяет `EvidenceSpan(source_id, content_sha256, start, end)` по точному UTF-8 хешу
полного тела источника. Смещения — Unicode code points, полуинтервал `[start,end)`. Цитата новости
содержит полное предложение или полный структурно законченный текст; банковская цитата — весь
проверенный фрагмент. Смещения страницы PDF не используются как смещения фрагмента. Неоднозначный
или обрезанный legacy-пересказ не повышается до доказательства. Точная однозначная legacy-цитата
может получить span автоматически. Прогноз/оценка банка и `reported_fact` имеют разные правила атрибуции.

Перед публикацией fact/assessment заменяется буквальным текстом проверенных spans. Перевод и
интерпретация относятся к выводам модели. `agent/semantic.py` проверяет все оставшиеся сгенерированные
утверждения, включая hypotheses, рекомендации, unavailable, horizon, поля scenarios и missing_data.
Вердикт связан с точным текстом, полем, профилем и закреплённым контекстом. Чужие/повторные/пропущенные
ID и неподтверждённые spans отвергают batch. Модельные spans у выводов заменяются только каноническими
фрагментами из принятого verdict. Причины verdict остаются в диагностической трассе; пользователю
показываются контролируемые сообщения об ограничениях.

Пределы одного batch: 48 кандидатов, 16000 символов кандидатов, 24000 символов полного контекста
источников и 10000 символов профиля (JSON-представления учитываются там, где они передаются).
Переполнение не оставляет непроверенный хвост. Проверка использует тот же `StructuredLLM`, budget
и deadline; один batch, без отдельного вызова на claim. `retries=0` допускает основную и запасную
модель — максимум два клиентских вызова; существующий transport может повторить HTTP400 JSON-mode
один раз на каждый из них. QA имеет такой же gate, не использует сохранённые выводы как доказательства,
сохраняет проверенные цитаты при частичном отказе и явно сообщает ограничение.

Эти ограничения проверяют соблюдение протокола и известных отрицательных примеров. Произвольное
смысловое следование всё ещё оценивается моделью и требует независимой live-приёмки.

`agent/critic.py`:
- факт и позиция банка должны ссылаться на источник из найденных
- позиция банка ссылается только на фрагменты аналитики банка
- числа в фактах должны подтверждаться источниками
- признаки компании должны быть в профиле
- все разделы карточки заполнены
- вывод опирается минимум на два признака компании, а не пересказывает новость
- условия договоров (ставка, срок, график) неизвестны: категоричное изменение платежа отклоняется; метка `hypothesis` сама по себе не заменяет смысловую проверку предпосылки
- личные инвестиционные советы («купите», «продайте», «инвестируйте») запрещены (`investment_advice`, ошибка)
- категоричные слова («обязательно», «гарантированно») дают предупреждение `categorical_language`

## Модели и лимиты

Разрешённые модели перечислены в `llm.py`, другие не вызываются. Лёгкая модель - разбор и план, основная - персонализация, запасная - если провайдер вернул ошибку. Лимиты на запуск: 3 итерации проверки, 12 вызовов инструментов, 40 000 токенов. Есть общий дневной лимит токенов.

### Бюджет в рублях

Лимит кейса - 500 руб. в сутки на общий ключ. Сервис считает свои вызовы в `Decimal` (`budget.py`): цена модели за 1000 токенов на вход и на выход, перед вызовом резервируется оценка, после ответа списывается фактическая стоимость. Вызов, который по оценке выходит за лимит, не отправляется (`budget_daily`). После ответа повторно проверяются фактические токены, стоимость и deadline: превышение остаётся в учёте, но не разрешает публикацию непроверенного текста. Такая проверка не отменяет уже списанные провайдером средства; для жёсткого денежного ограничения нужен также лимит на стороне провайдера.

| Потрачено за сутки | Что делает агент |
|---|---|
| меньше 350 руб. | работает как обычно |
| от 350 руб. | в начале запуска пишет в трассу `budget.level = warn` |
| от 450 руб. | пропускает необязательные шаги: повторный поиск по банку и исправление по замечаниям; карточка получает `limited` и пометку в `missing_data` |

Остальное:
- счётчик лежит в `TRACE_DIR/budget_state.json` (или `BUDGET_STATE_PATH`), переживает рестарт, окно сбрасывается в 03:00 по `BUDGET_TIMEZONE` (по умолчанию Europe/Moscow);
- цены задаются `LLM_PRICES_JSON`, для неизвестной модели берутся завышенные цены по умолчанию. **Тарифы провайдера пока не подтверждены**, без реальных цен рублёвый учёт приблизительный;
- сервис не видит расход других участников на тот же ключ: нужен запас в лимите или общий учёт на стороне Backend;
- на один запуск есть предел по времени `AGENT_MAX_SECONDS` (120 с): проверяется перед вызовом и после учёта ответа; незавершённый ответ даёт `failed`, а уже полученные проверенные цитаты могут сохраниться с явным ограничением;
- у каждого вызова LLM в трассе есть `call_id` и `cost_rub`, в финальном событии `usage` (токены, вызовы, рубли, длительность), `GET /health` показывает `daily_spent_rub`.

## Повторы и версии

- Запрос с `request_id`: повтор с тем же содержимым возвращает готовый инсайт (`cache_hit=true`, тот же `run_id`) без вызовов LLM; тот же `request_id` с другим содержимым - `409`. Одновременные одинаковые запросы выполняются один раз. Неудачный запуск (`failed`) не запоминается: повтор считается новым запуском, его стоит отправлять с `parent_run_id`. Соответствие `request_id` хранится в памяти процесса (не больше 500 последних), после перезапуска повтор выполнится заново.
- Готовые инсайты сохраняются в `TRACE_DIR/insights/`, поэтому `POST /v1/insights/{id}/questions` работает и после перезапуска. Папка содержит данные компаний, в гит не коммитится.
- Разбор события кешируется по хешу текста источников, `PROMPT_VERSION` и модели: изменение новости, промптов или правил проверки даёт новый разбор.
- `PROMPT_VERSION` - хеш файлов промптов и проверок (`agent/versions.py`), `GIT_SHA` берётся из переменной окружения при сборке. Оба, `request_id`, `parent_run_id` и модели пишутся в стартовое событие трассы.

## Безопасность

- текст новостей, аналитики банка и признаки компании (включая `user_provided`) передаются модели внутри блоков `<data>` как данные, инструкции из них не выполняются; последовательности `<data` и `</data` в тексте источника экранируются, закрыть или открыть блок из текста нельзя;
- подозрительные фразы в источниках («игнорируй все инструкции», `"tool": ...`, подделка тега `<data>` и т. п.) пишутся в трассу событием `injection_suspected` (источник и метки, без текста); это только журнал, текст не меняется;
- вызвать можно только инструменты из белого списка, аргументы проверяются по схеме; границы поиска по времени задаёт код, модель их расширить не может;
- действия в карточке - только рекомендации, сервис ничего не делает за пользователя;
- в трассу не пишутся промпты (только хеш и длина) и ключи.

## Срез по времени (`as_of`)

Необязательное поле запроса `as_of` фиксирует момент анализа: аналитика банка новее этой даты не используется, связанные новости после `as_of` (и новости без даты) не попадают в поиск, а событие позже `as_of` отклоняется при проверке запроса (`422`). Наивное время считается UTC. Без `as_of` окно аналитики задаётся датой события (или текущей датой, если даты нет), как и раньше. `as_of` пишется в стартовое событие трассы. Для проверки на новых событиях (D05) его нужно передавать явно.

## Трасса

События: `plan`, `tool_call`, `llm_call`, `check`, `adapt`, `error`, `final`. Схема - `contracts/ml/trace-event.schema.json`. Трасса пишется в JSONL и отдаётся через `GET /v1/runs/{run_id}/trace`.
