# Решение по D09 и D10: записка для обсуждения

Подготовлено 21 октября 2026 года. Основание — локальный `DOMAINS_AND_OWNERS.md`, разделы D09, D10 и таблица границ доменов. Оба домена принадлежат Лёше (Frontend). Документ требует предложений к обсуждению; по текущему запросу дополнительно создан запускаемый учебный прототип.

## 1. Что требуется и что предлагается

| Тип | Содержание |
|---|---|
| Требование D09 | Заметная и постоянно доступная точка входа на главном экране Альфа-Бизнеса |
| Требование D10 | Взаимодействие с аналитикой: уточнение, другой разрез либо первоисточник |
| Минимальный кандидат из файла | Источники и один уточняющий вопрос по карточке |
| Наше предложение | Главная + постоянное меню, лента, карточка, источники, один вопрос и три разреза |
| Учебное допущение | Две роли, три синтетические компании, два события; API возвращает подготовленные ответы |
| Неизвестно | Общий frontend-стек, дизайн-система банка, SSO, подтверждённые контракты, формат ссылок на закрытые PDF, задержки ML |

Ценность D09: пользователь быстро находит сервис и понимает, для какой компании он открыт. Ценность D10: после чтения вывода пользователь может проверить основание или уточнить следующий шаг. Наличие чата само по себе не доказывает полезность: ответ должен относиться к текущему событию и компании.

## 2. Теоретическая основа D09

**Информационная архитектура** — распределение содержимого по разделам и маршрутам. Для MVP достаточно трёх: главная, лента, карточка. Источник открывается отдельно, сохраняя исходную карточку. Не нужно создавать неработающие разделы «Платежи» или «Счета» ради сходства с банком.

**Обнаруживаемость** — возможность найти функцию без инструкции. На главной нужен блок с понятной пользой и конкретной кнопкой. Постоянный пункт меню помогает повторному входу. Это две точки доступа к одному сервису, а не два разных продукта. При проверке попросите коллегу самостоятельно найти аналитику; время поиска — внутренняя метрика команды, не норматив жюри.

**Контекст** — набор признаков, определяющих смысл данных. В нашем прототипе глобальный контекст — `company_id + role`, контекст карточки — дополнительно `event_id + view + insight_id`. Изменение любого значимого поля требует нового запроса и сброса прежнего уточнения. Название компании должно оставаться видимым, даже если пользователь перешёл по прямой ссылке.

**URL как состояние навигации.** Маршрут и несекретные идентификаторы помещены в hash URL. Он переживает перезагрузку и работает без настройки SPA fallback. В командном проекте можно использовать обычные маршруты React Router, если сервер возвращает оболочку приложения на deep link. URL не хранит право доступа: выбранный company_id сервер обязан проверить по сессии. Настоящие вопросы, банковские данные и секреты в URL не кладём. В прототипе вопрос живёт только в памяти страницы.

**Single source of truth** означает один источник текущего контекста. Здесь это нормализованный маршрут: из него выставляются селекторы, меню и параметры запроса. Если независимо держать компанию в URL, селекторе и локальном кеше, они могут разойтись. Для кеша в реальном frontend нужен полный ключ, например `[insight, company_id, role, event_id, view, version]`.

| Маршрут | Экран | Обязательный контекст |
|---|---|---|
| `#/home?...` | Главная, блок входа | Компания, роль, выбранный разрез |
| `#/feed?...` | Лента | Компания, роль; разрез переносится дальше |
| `#/insight/rate?...` | Карточка события | Компания, роль, событие, разрез |
| `/sources/news-rate` | Полный учебный источник | Проверяемый ID источника; новая вкладка |

Общие параметры: `company_id=retail&role=cfo&view=overview`. ID события находится в пути карточки. На главной и в ленте нет активного события. При выборе компании без аналитики прототип переводит карточку в пустую ленту.

## 3. Теоретическая основа D10

**Постепенное раскрытие:** лента даёт короткую причину значимости, карточка — объяснение и ограничения, источник — полное основание. Это снижает объём информации на первом экране и оставляет возможность проверки.

**Факт, оценка банка и вывод AI — разные типы знания.** Факт ссылается на событие. Оценка банка должна ссылаться на конкретный документ и дату. Вывод связывает факт с признаками компании и может быть условным. В учебном режиме вместо настоящей оценки банка явно показана синтетическая аналитика. Frontend не должен превращать любой текст модели в «позицию банка» и не должен самостоятельно достраивать отсутствующие числа.

**Разрез** — изменение представления одного анализа. В MVP «Риски» оставляет факт и влияние, «Что проверить» — действия. Данные и источники остаются согласованы. Это не симуляция нового экономического сценария. Роль пользователя — отдельное измерение: для CFO меняется акцент на договорах и финансировании, для CEO — на планах развития.

**Уточнение по карточке** отличается от общего чата: запрос должен указывать компанию, роль, событие, разрез и версию инсайта. В MVP один текущий вопрос и ответ; история диалога и разрешение местоимений между несколькими сообщениями не реализованы. Полноценный многошаговый диалог требует отдельного `conversation_id`, серверной истории и проверки контекста в D11/D12.

**Недостаток сведений — нормальное состояние.** `limited` означает, что часть ответа обоснована, но есть ограничения; `no_answer` — оснований для ответа нет. HTTP 200 уместен для обоих: запрос обработан, результат содержательно ограничен. Сбой сети/сервиса относится к технической ошибке и требует повтора. Пустая лента также не равна ошибке.

## 4. Асинхронность и гонки запросов

Пример ошибки: пользователь спрашивает о рознице, переключается на энергетику, а медленный ответ по рознице приходит позже. Если просто записать результат в экран, получится неверная персонализация.

Защита состоит из четырёх частей:

1. Перед запросом фиксируем неизменяемый снимок контекста.
2. При новом маршруте отменяем старые fetch через AbortController и увеличиваем `epoch`.
3. Перед отрисовкой проверяем, что `epoch` и номер вопроса всё ещё актуальны.
4. Сверяем context ответа, request_id и insight_id с запросом. Несовпадение — ошибка контракта, такой ответ не показываем.

Одна отмена недостаточна: ответ мог уже прийти и попасть в очередь обработки. Проверка поколения остаётся необходимой. Отмена fetch не гарантирует прекращение работы ML на сервере; серверное прерывание и бюджет — D07/D11. В нашем API есть 15-секундный frontend timeout и повтор вручную.

Источник: [MDN — Using Fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch). Это документация браузерного механизма, а не норматив хакатона.

## 5. Состояния интерфейса

| Состояние | Как распознать | Что видит пользователь | Следующее действие |
|---|---|---|---|
| Загрузка | Запрос выполняется | Статус, placeholder, aria-busy | Можно сменить компанию или раздел |
| Готово с ограничениями | Карточка получена | Вывод, источники, неизвестные данные | Источник, разрез, уточнение |
| Пусто | `items=[]` | Объяснение отсутствия событий | Сменить компанию, вернуться на главную |
| Нет ответа | `status=no_answer` | Причина и необходимые данные | Уточнить вопрос / собрать данные |
| Ошибка | Сеть, timeout, 4xx/5xx | Понятное сообщение, «Повторить» | Повтор в том же контексте |
| Устаревший контекст | ID/версия не совпадают | Ошибка вместо чужого ответа | Заново открыть карточку |

Форма допускает до 1000 символов. Пустой вопрос не отправляется. Во время отправки основная кнопка заблокирована; быстрый вопрос заменяет предыдущий запрос. Уточнение очищается при смене компании, роли, события или разреза. После reload оно не восстанавливается — это осознанное упрощение, не потеря серверной истории.

## 6. Доступность и безопасное отображение

Используем настоящие `button`, `a`, `select`, `label`, `textarea`; все поля имеют подпись. Кнопки доступны клавиатурой, фокус виден. При переходе экранов фокус переносится на main; при получении уточнения не отрывается от формы. `role=status` сообщает ход операции, `role=alert` — ошибку; отсутствие ответа обозначено текстом, не только цветом. Навигация помечает активный раздел `aria-current`, разрезы — `aria-pressed`.

Источники: [W3C — Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html), [W3C — Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible). Полная проверка соответствия WCAG не проводилась; перечислены конкретные реализованные меры.

Ответы вставляются через `textContent`, не через HTML модели. Ссылки разрешаются по ID сервером; произвольный URL модели не становится ссылкой. Для реальных внешних источников серверу нужен allowlist схем `https/http`, запрет `javascript:` и проверка прав на закрытые документы. Новая вкладка получает `noopener noreferrer`. CSP ограничивает ресурсы текущим origin. Синтетический сервер не реализует SSO: в интеграции backend проверяет пользователя, разрешённые компании и источники при каждом обращении. Нельзя считать селектор компании средством авторизации.

## 7. Варианты решения и выбор

| Вариант | Состав | Преимущества | Ограничения |
|---|---|---|---|
| A — выбранный стенд | HTML/CSS/JS, hash-маршруты, Python API-заглушка | Запуск одной командой, без npm и LLM-ключа, проверяемые состояния | Ручная маршрутизация; подготовленные ответы; перенос в общий frontend |
| B — командное приложение | React/TypeScript, роутер, общий API-клиент, дизайн-система | Типизация контрактов, переиспользование компонентов, интеграция с командой | Нужны утверждённый стек, сборка и согласованный backend |

Для демонстрации доменов сейчас используем A. Если команда уже работает на React/TypeScript, для общего MVP целесообразен B с переносом поведения и контрактов, а не включением второй самостоятельной оболочки. Предлагаемые компоненты: `BankShell`, `CompanyRoleSelector`, `HomeEntry`, `InsightsFeed`, `InsightPage`, `EvidenceLinks`, `ClarificationForm`, `RequestState`.

## 9. Пример результата

Компания «Учебная розница», CFO, событие о ставке. UI показывает факт сохранения ставки; отдельный синтетический аналитический фрагмент об условиях финансирования; условное объяснение связи запасов с оборотными средствами; действие «проверьте сроки и тип ставки». Вопрос «Сколько составит эффект?» получает `no_answer` с перечислением недостающих данных. Смена на энергетику меняет объяснение на инвестиционные проекты. Это демонстрация контрактов и контекста, а не подтверждённый экономический анализ реальных компаний.

## 11. Трудоёмкость, блокеры и следующий шаг

Оценки для одного frontend-разработчика после согласования API: оболочка и маршруты — 3–5 часов; лента и карточка — 4–6; источники и уточнение — 3–5; состояния, гонки запросов, адаптивность и проверка — 4–6. Итого ориентировочно 14–22 часа; интеграция с нестабильным backend и перенос в банковскую дизайн-систему оцениваются отдельно. Это предложение для планирования, не обещание срока.

Блокеры реальной интеграции: формат D02-ответа; настоящие ссылки и права на PDF; идентификаторы компаний/ролей; время выполнения D11; согласованный стек. Пока их нет, API-заглушка позволяет разрабатывать и проверять UI.

Отложить можно многосообщенческий чат, уведомления, избранное, экспорт, визуализацию платёжного графа и сохранение персональных настроек на сервере. Сохранение контекста, честные ограничения, ошибки и источники откладывать нельзя.

На обсуждение принести: запущенный стенд, эту записку, API-контракт и результаты проверки. Решения, которые нужно принять с командой: вариант общего frontend, окончательная структура инсайта, источник сессии и доступов, синхронный или фоновый D11, правила сохранения истории уточнений.
