## Граница подключения

По умолчанию используется demo. Чтобы включить server, загрузить собственный скрипт конфигурации после integration.js и перед app.js. Он должен присвоить window.INSIGHTS_CONFIG = {mode: 'server', bindings}. Все семь функций bindings обязательны. Неполная конфигурация показывает ошибку, без тихого переключения на демоданные.

Каждая функция получает (input, {signal, requestId, transport, onProgress}). Использовать только публичный Java API /api/v1 через same-origin reverse proxy. ML API из браузера не вызывается. transport отправляет cookie same-origin; демонстрационный bearer и ключ LLM в код и localStorage не помещать. Если API требует другой способ аутентификации или CSRF-заголовок, согласовать его до подключения.

| Binding | Вход | Выход для UI |
|---|---|---|
| bootstrap | {} | {profile:{name,company_id,role},companies:[{id,name,sector,roles?}],roles:{код:название},views:{код:название},notice} |
| feed | {company_id,role} | {context,items:[{id,title,category,date,why}],as_of,empty_reason?} |
| insight | {company_id,role,event_id,view} | Модель карточки API_CONTRACT.md + outcome, outcome_message |
| clarify | Контекст + insight_id,question,request_id | {context,insight_id,request_id,status,text,sources,outcome?} |
| preferences | Контекст экрана | Словарь состояния, описанный ниже |
| savePreference | {context,key,value,insight_id?} | Успешное завершение только после серверного подтверждения |
| opened | {context,insight_id} | Подтверждение регистрации открытия |

Это внутренний контракт UI, а НЕ утверждение о текущем формате Java DTO. Не применять универсальное переименование camelCase: структура карточки и связи утверждений требуют явного преобразования. Согласованный mapper должен валидировать обязательные поля, контекст и версию, сохранять исходные ID и не дописывать факты, отсутствующие в ответе. Права на компанию и роль всегда проверяет backend. companies[].roles ограничивает выбор в UI, но не заменяет авторизацию.

Ключ скрытия: company_id:role:event_id. Ключ оценки: company_id:role:event_id:insight_id. Binding переводит их в реальные серверные идентификаторы; не разбирать произвольные ID простым split(':'). Использовать context и insight_id отдельно. Скрытие и оценка — разные операции. В server режиме localStorage не является источником профиля/оценок и не служит запасным серверным хранилищем.

Карточка сохраняет blocks, sections, sources, missing_data и disclaimer из текущего API_CONTRACT. outcome: COMPLETE, LIMITED, INSUFFICIENT_DATA, NO_RESULT, FAILED. LIMITED показывает доступный текст с предупреждением; остальные неполные терминальные состояния не показываются как готовый полный инсайт. Неизвестный outcome также не выдаётся за успех. Уточнения имеют собственный outcome. Пустая лента может передать понятное empty_reason.

## Операции и повторы

transport(path, options) допускает только адреса текущего origin под /api/v1/. Первый POST передаёт requestId как Idempotency-Key (имя заголовка подтвердить с BE-08). Опрос не повторяет POST. Ответы 202 или статусы QUEUED/PENDING/RUNNING продолжают ожидание. Location обязателен для первого ответа ожидания; последующие ответы могут использовать тот же URL. Retry-After поддерживает секунды и HTTP-date, интервал ограничен 0.5–30 сек. Один HTTP-запрос ограничен 15 сек, ожидание операции — примерно 120 сек. Уход со страницы отменяет ожидание, но не обещает остановить серверную генерацию.

Для нормализации результата с поддержкой продолжения использовать:

~~~js
return InsightsIntegration.mapOperation(
  () => transport(agreedPath, {signal, requestId, onProgress}),
  agreedDtoToViewModel
);
~~~

agreedPath и agreedDtoToViewModel здесь обозначают значения из будущего согласованного контракта, это не готовый Java binding. Если операция завершена ссылкой resultUrl, binding должен отдельно получить ресурс и проверить контекст. При исчерпании ожидания ошибка содержит operationURL и resume(signal); mapOperation сохраняет нормализацию при продолжении. UI удерживает продолжение в памяти и при повторе того же запроса опрашивает операцию без нового запуска. После перезагрузки восстановление операции требует отдельного согласованного backend-контракта. Повтор вопроса после сетевой ошибки использует прежний request_id. Сервер обязан обеспечить идемпотентность. Автоматических повторных платных запусков нет.

## Источники и требования хакатона

Условие, стр. 9–10 и 14: сохраняются вход из главной, контекст компании/роли, тематические разрезы, уточняющий вопрос и основания выводов. FAQ 43–44, 48–49: факты, оценки банка, AI и гипотезы разделены; дисклеймер сохранён; отсутствие материала не заменяется вымышленной позицией банка. FAQ 52–54 и 73: оболочка интернет-банка остаётся; реальная банковская интеграция для хакатона не обязательна. FAQ 61: узкие экраны — улучшение доступности веб-интерфейса, не отдельный критерий мобильного продукта. FAQ 62: сохранены открытие, скрытие, оценка и переход к источнику. Следующее действие/CRM не реализовывается в рамках FE-08–FE-13.

SourceRef преобразуется в {id,title,url,date?,page?,excerpt?}; section — в {kind,text,certainty,source_ids,claim_id?,feature_refs?}. ID источника остаётся непрозрачным: путь по нему не строится в server режиме. Разрешены http/https, относительные URL разрешаются относительно сайта. javascript/data/file URL, управляющие символы и URL с credentials отклоняются. Недоступная ссылка показывается текстом, а не исчезает. Страница добавляется как #page=N. Для защищённого PDF нужен серверный маршрут с cookie-доступом или согласованный механизм выдачи ссылки: anchor не добавляет Authorization. claim_id хранится на DOM-контейнере основания, excerpt и признаки видны текстом. URL и подтверждения должен поставлять backend, не свободный текст LLM.
