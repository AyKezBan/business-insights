# Смысловая приёмка материалов: синтетические случаи v1

`material-semantic-cases.jsonl` содержит 12 синтетических классов ошибок и 29 недопустимых вариантов утверждений. Это данные для регрессионного harness T10, а не результаты приёмки, не реальные публикации CBR/FNS/EIA/банка и не закрытый holdout. Домены `example.invalid` намеренно не открываются. Числа, даты, названия организаций и reviewed-статус банковского фрагмента заданы только внутри fixtures.

Формат `material-semantic-cases/v1` независим от production wire DTO. Файл **не** является входом существующего `insight_agent.evaluation.load_manifest`: в нём нет обязательного `request`. Адаптер тестов должен строить запросы через реальные схемы и registry после интеграции T07, сохраняя этот набор условий. Не менять production API под fixture и не выдавать успешный JSON parse за смысловой PASS.

## Содержание записи

- `sources[].text` — точный разрешённый текст данного синтетического source ID; `content_sha256` — SHA-256 его UTF-8 байтов. Никакой скрытой полной статьи нет. `text_scope=annotation` явно ограничивает доступные сведения.
- `active_source_ids` выбирает версии, доступные текущему corpus. В SEM06 старая версия сохранена в `sources`, но не входит в active. Указанный `corpus_revision` — стабильный синтетический digest выбранных ID/hash, а не реальная опубликованная revision registry.
- `profile_context.known` и `.unknown` задают семантические факты и пробелы. Это тоже не wire DTO. Не превращать неизвестное значение в `false`, `0`, отсутствие продукта или известную экспозицию.
- `unsafe_candidates` содержит буквальные подмены. `inject_into` перечисляет поверхности, на которых их нужно проверять, включая скалярные поля и QA. Для поля с другим типом тест подставляет текст в корректную оболочку, чтобы проверка доходила до смыслового gate, а не падала при парсинге.
- `positive_control` — подтверждённая цитата и корректный span. Смещения — Unicode code points, полуоткрытый интервал `[start,end)`. SHA относится к полному `sources[].text`, а не к цитате, странице, заголовку или конкатенации другой версии. Для банка span покрывает весь fragment.
- `expected_safe.answer_text` — образец допустимого ответа; это семантический критерий, а не обязательное побайтовое совпадение. В случаях перевода факт можно оставить точной английской цитатой с отдельно проверенным русским пояснением. `safe_claim_must_survive` запрещает проходить проверку отказом на всех случаях.

## Проверка конечного результата

Для каждого из 29 unsafe-вариантов независимо:

1. Собрать корректный синтетический event/profile и pinned corpus из разрешённых источников. Отключить сетевой research; использовать существующий `StructuredLLM` с локальным scripted client. Не читать ключи и не запускать платную модель.
2. Подать ошибку в analyst facts, personalization claim и QA claims; отдельно проверить свободные поля. Сохранить остальные поля валидными, чтобы ошибка не маскировалась несвязанным schema/required-section отказом.
3. Довести запуск до опубликованного `Insight`/`Answer`, API mapping и renderable text, когда соответствующий harness доступен. `check_claims()` без final output недостаточно: assembly, fallback или mapper могут вернуть удалённый draft.
4. Убедиться, что ложное утверждение не опубликовано ни как факт/оценка, ни как уверенный inference, ни в headline/rationale/scenario/missing-data/answer text. Верная цитата рядом с ложным выводом не делает результат допустимым. Отдельно проверить semantic verdict/reason, сохранённые source/span/claim IDs и trace.
5. Проверить положительный контроль: подтверждённая цитата остаётся доступной с правильным источником, датой, условием и единицей. Если неизвестен только ответ на вопрос, сохраняется полезный подтверждённый факт и объясняется конкретный пробел.

Не принимать тест, который проверяет только отсутствие буквальной строки: модель может выразить ту же ошибку другими словами. Литеральный assert полезен как regression, но смысл, источник и окончательная форма вывода проверяются отдельно. Само название `hypothesis` не оправдывает ложную внешнюю предпосылку. Допустима только действительно условная гипотеза, которая не выдаёт неизвестное за установленный факт.

| ID | Класс | Что должно остаться неизменным |
| --- | --- | --- |
| SEM01 | Участник и объект | Регулятор, манипулировавший участник и эмитент различаются |
| SEM02 | Отрицание | «Не продлевает» не превращается в «продлевает» |
| SEM03 | Будущее и совершённый факт | План платежа не означает исполнение |
| SEM04 | Период FX | Значение связано со своей датой, валютой и базовой единицей |
| SEM05 | Единицы/валюта/знак | Все четыре варианта: bp/percent, направление, USD/RUB, −/+ |
| SEM06 | Исправление версии | В новой revision действует 14; старая 13,5 доступна только в старом контексте |
| SEM07 | Неполная аннотация | Нет выдуманной даты, срока или штрафа |
| SEM08 | География | США не превращаются в Россию |
| SEM09 | Перевод EIA | Прогноз, условие, рост, 2%, США и 2027 сохраняются вместе |
| SEM10 | Атрибуция банку | Внешняя оценка не становится позицией банка |

Старый результат не «исправляется» чтением текущего индекса. Это проверка версии, а не настоящее восстановление рыночной информации на прошлую дату. `as_of` имеет смысл publication cutoff; позднее наблюдение/исправление и ограничения такого cutoff показываются явно.

## Спаны: отдельные механические проверки

Положительный bank span в SEM11 равен `[0,len(fragment.text))`. Ниже нужны отдельные негативные варианты поверх валидного источника:

- неизвестный source ID; hash другой версии или hash самой цитаты вместо полного source text;
- отрицательная, обратная или выходящая за границы пара offsets; пустой span;
- начало после отрицания, внутри слова или придаточного условия; конец до существенного ограничения;
- частичное предложение вместо полного исходного предложения; для банка одно предложение вместо всего проверенного fragment;
- `char_start/char_end` страницы, ошибочно использованные как offsets банковского fragment;
- Python code points против UTF-16 code units: отдельный текст `📌 Справка.\nФНС не продлевает срок уплаты налога.`; корректный start — `len("📌 Справка.\n")`, а не длина JS UTF-16 строки. Проверить кириллицу и символ минуса `−` без неявной нормализации;
- правильная цитата/spans в одном claim и ложная внешняя предпосылка в соседнем inference, scenario или free field.

Проверять корректные границы без произвольной нормализации текстов после вычисления SHA. Не доказывать arbitrary entailment одним regex. Numeric/reference checks остаются полезной частью gate и не заменяют faithful rendering и structured semantic verdict.

## Бюджет и fail-closed

Verifier использует тот же `StructuredLLM`, run budget, deadline и tracer, что analyst/personalizer. Нет второго автономного клиента, отдельного безлимитного вызова или сетевого запроса в тестах. Зафиксировать число semantic calls, retries/fallback, usage и завершение по deadline.

Обязательные ошибки verifier: schema error, транспортная ошибка, budget exhausted, timeout, пустой/неполный verdict, неизвестный или повторённый claim/span ID. Непроверенный draft не публикуется после любой из них. Особенно проверить путь, где personalization уже создан, а verifier выбросил исключение: существующий outer catch не должен заменить semantic gate одними deterministic checks.

QA проходит тот же принцип; `no_answer` должен объяснять пробел. Удалённые утверждения не возвращаются через draft.text, missing_data, scalar fallback или mapper. Не признавать весь корректный ввод `failed`, если есть полезный подтверждённый результат; для полного отсутствия поддержанного результата допустим явно объяснённый refused/no_answer. Нельзя помечать outcome full/complete, когда проверка не состоялась.

## Рубрика и запись результата

Для каждого case/candidate/surface отдельно записать:

- git SHA, prompt/rules version, fixture SHA, runtime/schema/corpus revision, source hash, profile version, request/run/insight/answer IDs;
- точную проверенную поверхность и итоговый опубликованный текст, kept/dropped claim IDs и spans, semantic verdict/reason;
- результат `PASS`, `FAIL`, `BLOCKED` или `NOT_RUN`, причину, фактические calls/tokens/cost/deadline;
- независимый ручной verdict по участнику, отрицанию, дате, числу, единице, географии, модальности, условию, атрибуции и экспозиции.

`PASS` требует одновременно: 0 опубликованных смысловых подмен; положительный контроль сохранён; все связанные ссылки/версии верны; QA и свободные поля не обходят gate; отказ/ограничение объяснены; при ошибке verifier нет unchecked result. Один непройденный обязательный пункт означает `FAIL`. Незапущенные DB/browser/live проверки остаются `NOT_RUN`, внешняя недоступность — `BLOCKED` с владельцем.

Набор синтетический и открытый для разработки. После исправления дефект становится regression, а соответствующий класс оценивается на новом независимом holdout. Offline PASS показывает работу механизма и не означает A10/G09 live acceptance. Платные прогоны и итоговые 9 event×profile + QA выполняет C0 только после общего budget gate; этот fixture-пакет не предоставляет такого разрешения.
