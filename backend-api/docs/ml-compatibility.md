# Интеграция с ML

Источник контрактов — общие `contracts/ml/*.schema.json`. Ресурсные копии схем backend совпадают с ними побайтно. Модели `MlContracts` сохраняют все согласованные поля и десятичную точность денежных показателей. Версия объединённого адаптера — `materials-feed-v3`; `CONTRACT_COMMIT` обозначает историческую интеграционную базу.

## Ошибки и длительные операции

Клиент ограничивает время запроса и размер ответа, не повторяет POST автоматически. После таймаута завершение операции ML неизвестно.

- HTTP `422` и прочие `4xx` — отклонение запроса; `429` — ограничение частоты; `5xx` и ошибки связи — недоступность сервиса.
- Некорректный JSON, нарушение схемы или несовпадение идентификаторов — недопустимый ответ ML.
- HTTP `200` со статусом `failed` или `no_answer` сохраняется как отдельный исход, а не как транспортная ошибка.

Инсайты и контекст вопросов сохраняются в `TRACE_DIR/insights` и восстанавливаются после рестарта при сохранённом хранилище. QA использует контекст родительского анализа и закреплённую revision. При отсутствии сохранённого контекста возможен `404`; при недоступности исходного корпуса возвращается `no_answer`, без подстановки текущих материалов.

## Каталог и обновление ленты

ML `GET /v1/materials/events` сохраняет контракт #8: `catalog_token`, `events`, `next_cursor`. Отдельный `GET /v1/materials/news` возвращает `corpus_revision`, `items`, `next_offset`; для следующих страниц можно закрепить `revision`. Оба чтения не вызывают модель. Каталог использует cursor и полный CatalogToken, а выдача новостей — offset и сортировку по дате публикации.

Java refresh использует проверенный каталог с CAS, выбирает события от новых к старым и отвечает HTTP `200` с результатами отбора. Созданные операции анализа выполняются асинхронно и читаются отдельно по `operationId`. Фиксируются профиль, событие, роль, срез времени, revision/hash и версия события до постановки в очередь. Worker не перечитывает текущий профиль. Новая версия события исключает прежние результаты из текущей ленты; ещё не начавшаяся устаревшая операция завершается `NO_RESULT`.

Каталожные события исправляются через публикацию нового корпуса, а не ручной PUT. Изменение semantic event hash создаёт историю версии и помечает предыдущие операции stale. Обновление только банка меняет revision корпуса без увеличения версии неизменившегося события. Старые QA/PDF остаются закреплены за исходным корпусом.

## Доказательства и профиль

ML DTO, JSONB и публичный API сохраняют claim IDs, `evidenceSpans`, метаданные и выдержки источников, точность дат, конфликты, outcome/error/request и контекст корпуса. В `conflicts` передаются конфликты результата ML, в `sourceConflicts` — принятого исходного события. UUID операции отличается от logical event ID и ML insight/run ID.

Фрагменты оснований содержат source ID, SHA-256 и границы `[start,end)` в Unicode code points. Старые записи без spans получают пустой список. При наличии SourceRef hash он сверяется с hash фрагмента. Java/UI не вырезают текст заново по смещениям.

Выручка 0..999 сохраняется; ровно 1000 остаётся placeholder. Передаются год, статус и scope выручки, доступность ФТС, период платежей и quality notes. Неизвестный период отмечается явно. Отсутствие сведений ФТС не доказывает отсутствие торговли; страны не устанавливают импорт/экспорт. Платёж не доказывает роль поставщика/покупателя. Исходные индексы `counterparties[i]` сохраняются при сортировке ML. Неизвестная выручка группы остаётся неизвестной.

Потерянные прежними адаптерами поля исторических результатов автоматически не восстанавливаются. Структурная проверка не заменяет смысловую приёмку AI. Правила отбора и версий: [feed-refresh.md](feed-refresh.md).
