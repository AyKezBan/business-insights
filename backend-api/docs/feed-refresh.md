# Новости, версии событий и обновление ленты

`POST /api/v1/companies/{companyId}/insights/refresh` с телом `{"role":"cfo"}` связывает готовый корпус новостей с персональной лентой. Доступ к компании проверяется до чтения корпуса и постановки операций. Это явный запрос на анализ, который может инициировать платные обращения к ML. Обычный GET ленты не запускает анализ.

1. Backend получает полный проверенный каталог ML через `MaterialCatalogService` и атомарный CAS. Из него выбирается страница новостей в порядке даты публикации и ID по убыванию, с полными SourceRef и conflicts. Runtime подхватывает новые публикации без рестарта. Для refresh нужен опубликованный trusted catalog; legacy JSONL сам по себе его не создаёт. Отдельный ML endpoint `/v1/materials/news` предоставляет offset-выдачу, не меняя формат `/v1/materials/events`.
2. Каталог проверяется по ML-схемам, полному publication token, хешам и связности конфликтов. Opaque ID материалов сохраняются без ограничений формата ручного EventInput. Новые ID регистрируются, semantic corrections создают следующую версию; повтор публикации не создаёт версий и не откатывает каталог. Исходные ID, URL, хеши, выдержки и конфликты сохраняются в JSONB.
3. `EventRelevance` оценивает совпадение тем с каналами ОКВЭД, продуктами, наличием сведений ФТС и контрагентов. Совпавший канал даёт 25 баллов, соответствие роли добавляет 10, слова вида деятельности дают 30, региона/города — 20. Итог ограничен 100, порог отбора — 20. Одна роль без признака профиля не делает событие релевантным. Причины возвращаются для каждого кандидата. Это начальные объяснимые правила, их качество не откалибровано на размеченной выборке.
4. Срок актуальности — `FEED_MAX_AGE` (по умолчанию 30 дней, допустимо до 365) от публикации, при отсутствии timestamp — от даты источника, при отсутствии обеих дат — от приёма версии. События старше срока и с публикацией более чем на пять минут в будущем не попадают в автоматический отбор.
5. Подходящие кандидаты сортируются по релевантности и ID. По умолчанию создаётся до восьми новых операций, `maxAnalyses` допускает 1..16. Используются прежние очередь, состояния операций и защищённый polling. Поля `sourceLimit` (1..100) и `sourceOffset` (0..1000000) управляют страницей корпуса; `nextOffset=null` обозначает конец. При смене `corpusRevision` обход надо начать заново.
6. Ключ обновления зависит от полного профиля, роли, ID и версии события, revision корпуса и semantic event hash. Повтор возвращает `EXISTING_OPERATION`, включая уже завершившиеся ошибкой операции, без нового платного вызова. Существующие операции не расходуют лимит новых анализов. `DEFERRED_LIMIT` и `DEFERRED_QUEUE_FULL` можно обработать повтором той же страницы. Новая попытка после ошибки/таймаута требует явного `/analyses` с новым ключом. Автоматического повтора нет.

Готовые карточки сортируются по `relevanceScore`, затем `impactLevel`, времени создания и UUID. Для события остаётся последняя опубликованная карточка выбранной компании, роли и владельца. Скрытие применяется к этой карточке. Старые версии и просроченные события в ленту не попадают. Пустая лента остаётся нормальным результатом. Ручной `/analyses` принимает и старые/низкорелевантные события: результат доступен по ID, но действуют правила публикации в ленте.

## Исправления и история

Прежний `POST /events` сохраняет поведение: идентичный повтор допустим, другое содержимое того же ID даёт `409 EVENT_ID_CONFLICT`. Ручные события исправляются через API ниже; каталожные — только публикацией нового корпуса (`MATERIAL_EVENT_IMMUTABLE` при ручном PUT). Для ручного исправления:

- `GET /events/{eventId}` возвращает текущие `version`, `contentHash`, `receivedAt` и `event`.
- `PUT /events/{eventId}` принимает `{"expectedVersion":1,"event":{...}}`. ID в теле должен совпадать с адресом. Изменённое содержимое требует актуального номера версии, иначе `409 EVENT_VERSION_CONFLICT`. Повтор текущего содержимого идемпотентен.
- `GET /events/{eventId}/versions?limit=20&offset=0` возвращает историю в порядке убывания версии.

Миграция V3 (после каталожной V2) переносит имеющиеся события в версию 1 и привязывает существующие операции к ней. Профиль, полное ML-событие, версия, роль и corpus/cutoff context фиксируются одной записью до очереди; worker использует этот request, без повторного чтения профиля. Постановка в executor происходит только после commit. Коррекция помечает прежние операции `stale=true`. Не начатый анализ устаревшего события завершится `NO_RESULT` без вызова ML. Уже выполняющийся ML-запрос не отменяется, его результат сохраняется устаревшим и не публикуется в ленте. Карточка по ID показывает `stale`, `eventVersion`, `expiresAt`, релевантность и конфликты своего снимка.

Синхронизация считает загруженный корпус источником текущего содержимого. Повтор уже известной ревизии защищён от отката. Для ранее не встречавшегося содержимого из старого независимого снимка нет внешнего монотонного номера события: такая публикация будет новой backend-версией. Поэтому обновления должны читать актуальный экземпляр ML, а ручные конкурирующие исправления используют `expectedVersion`.

Обновление ленты новой версией требует явного refresh или анализа с новым ключом. Отдельный планировщик, подписки на все компании и изменения UI в эту реализацию не входят. Runtime читает новые публикации без рестарта; начатый анализ и QA сохраняют исходную revision.

Refresh возвращает HTTP `200` с результатами отбора. Каждый `operationId` опрашивается отдельно; общего Location для batch-ответа нет.
